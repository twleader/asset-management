# Product Steering — 資產管理系統

> **用途：** 本文件由 AWS KIRO SDD 在每次對話中載入，提供「產品是什麼、為誰、為什麼」的長期 context。`requirements.md` 描述具體 AC，本文件描述產品的不變定位與優先順序。

---

## 1. Product Vision

**一句話定位：**

> 為個人投資者打造的「多資產一站式追蹤平台」，整合銀行存款、台股、美股、信託基金，並以歷史快照（snapshot）為核心，提供任意時間點的完整資產樣貌、損益歸因與歷史趨勢。

**核心信念：**

1. **快照是唯一真實來源（Single Source of Truth）。** 任何「當時的資產狀況」皆對應一筆 `AssetSnapshot`；不靠交易流水即時推算總資產，而靠每段時間定錨的快照避免漂移。
2. **股價一律是成交價。** 系統所有顯示的股價（盤中、收盤、走勢圖、Dashboard、即時估值）必須是真實成交過的價格，不得使用買賣中價、買價、賣價或衍生估算值。
3. **設定全資料庫化，零硬編碼分類。** 銀行、券商、存款類型、市場類型、待轉入資金類型、信託基金主檔皆由 UI 管理，不寫死於程式碼。
4. **同義欄位 = 同一支 business service API。** 不同頁面顯示相同意義的值（即時股價、預估配息、收盤價⋯）必須走同一條資料路徑，避免畫面不一致。

## 2. Target Users

| 角色 | 描述 | 核心需求 |
|------|------|----------|
| **個人投資者（單一使用者）** | 自行管理多元資產的散戶，每月／每季手動建立快照 | 一鍵看到當下總資產、了解歷史變化、知道收益來自哪 |
| **未來擴展（暫不支援）** | 多帳號、家庭共用、財顧協作 | 目前架構為單使用者，無 auth 模組 |

> 本系統支援多使用者（Gmail OAuth2 登入 + 以 `owner_user_id` 做多租戶資料隔離，見 Requirement 28），以 Docker Compose 一鍵啟動於自架環境。

## 3. Primary Use Cases

依使用頻率排序：

1. **每日早晨打開 Dashboard 看資產總覽** — KPI 卡片（資產總計 / 存款 / 信託基金 / 股票現值 / 預估年配息）、資產配置圓餅圖、歷史趨勢線、持股表格（含即時股價，盤中每 2 分鐘自動刷新；SSE 推播）。
2. **每月／重要時點建立快照** — `SnapshotForm` 填銀行存款、股票持倉、基金持倉、匯率，系統自動帶歷史收盤價與歷史匯率，按下儲存即定錨該時間點。
3. **盤中觀察股價與警示** — 觀察清單（衍生自 `stock_alert`）顯示即時行情、技術指標、最近觸發資訊；雙擊任一檔開啟 K 線走勢圖 + 月／季／年線 + 股利歷史 + ETF 持股明細。
4. **檢視歷史趨勢與年度表現** — 「歷年資產管理」表格、總資產趨勢圖、堆疊長條圖、台股／美股／台幣存款／美元存款分列。
5. **記錄已實現損益** — 每筆股票買賣記錄，依年度彙總獲利率。
6. **匯率／交易日曆／GDP-TWSE 對照** — 輔助分析。
7. **資料備份／還原** — UI 觸發 `pg_dump` 加密上傳 Google Drive，含台股／美股交易日自動排程；可挑歷史備份還原（含自救點）。

## 5. Out of Scope（明確不做）

- **多使用者 / 認證 / 授權** — 已於 Requirement 28 導入（Spring Security OAuth2 Gmail 登入 + 多租戶資料隔離），不再屬 Out of Scope。
- **真實券商下單** — 絕對禁止。系統只做記錄、分析與建議；不得透過任何券商 API／SDK 建立、送出、買入、賣出、改單、撤單或重送委託。使用者若採納建議，須自行在券商官方介面操作。
- **加密貨幣、保險、不動產** — 目前資產類別限存款／股票／基金；新增類別需走 SDD 重新評估。
- **行動 App** — Web SPA（Vue 3）即為使用者介面；響應式但非原生 App。
- **Excel 批次匯入** — 原 `ExcelImportService` 已停用 controller endpoint，僅保留匯出。

## 6. Non-Functional Priorities（依優先序）

1. **資料一致性 > 即時性。** 寧可慢一拍也要保證 KPI 與分項加總相等、各頁同義欄位顯示同一數字。
2. **歷史可回溯。** 快照 + Liquibase + 自動備份輪替（daily 50 份 / weekly 5 份 / manual 5 份）三道防線；任何商業邏輯變更須能回放舊資料。
3. **外部 API 失敗不拖垮主系統。** 抓價子系統獨立為 `external-materials-service` container；fail-soft 採用 Redis miss → `stock_price_history` fallback。
4. **單機可運行。** 全套 Docker Compose 啟動於個人 Mac／NAS 即可，不依賴雲端託管服務（除 Google Drive 作為備份目的地）。
5. **嚴格遵守 SDD 流程。** 任何商業邏輯變更必須先動 `spec/`（requirements → design → 自足任務檔 → `/spec-review` 審查通過）再動 code；commit-msg hook 驗「spec/ 有無變更」，內容正確性由審查閘門把關。

## 8. Product Principles for Future Decisions

當未來面對新需求或重構決策時，依以下優先順序判斷：

1. **是否破壞「同義欄位 = 同一邏輯」？** 若是，必須改為走同一支 service API（即使要重構）。
2. **是否破壞「股價一律是成交價」？** 若是，必須拒絕或重新設計來源。
3. **是否引入跨資料表冗餘？** 若是，必須在 spec 註明刻意 denormalization 的理由（如歷史快照凍結值）。
4. **是否要加 Enum 寫死分類？** 一律不行；新增分類欄位走資料庫主檔 + UI 管理。
5. **是否新建前端頁面 → 直接打 business service？** 一律不行；必須建立對應 BFF controller（即使只是 passthrough）。
