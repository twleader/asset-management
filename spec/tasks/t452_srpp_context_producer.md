# [t452] SRPP 共用計算結果：資料表、政策 registry 與背景 producer（business-services）

**對應 Requirements:** Requirement 163（9090 SRPP 共用計算結果唯讀 API 首個可交付版本：背景 producer 凍結來源、計算 assets／allocation／基礎收益並原子發布不可變 package；registry 為空時 fail-closed）
**前置任務:** 無
**Liquibase changeset:** v1.136.0-srpp-daily-context.sql

## 背景

使用者交付 SRPP 提案規格包（原封保存於 `docs/handoffs/srpp-api-spec-20260923/`），要求資產管理系統以背景 producer 把固定公式先算好、凍結來源、發布成不可變 package，再由 9090 GET 唯讀讀取（讀取端點是 t453、BFF／gateway 是 t454）。本任務只做 business-services 的「寫入側」：DB schema、政策 registry、owner-explicit 來源讀取、五模組計算、原子發布、保留期清理與離線登錄腳本。

使用者 2026-09-25 決定：只做「首個可交付 API」（assets／allocation／基礎收益可用，funding、completedTechnicals、稅後現金流具名 UNAVAILABLE），registry 上線時為**空表**、不登錄任何規則包；空 registry 時 producer 不做任何計算。SRPP 專案本身不修改。

既有事實（已查證）：
- `LatestAssetsService.getLatest()`、`StockPriceService.getLiveAssets()` 靠 `snapshots.findLatestWithStocks()`，而 owner 過濾由 `TenantFilterAspect` 只在「有 HTTP request context」時啟用；**背景執行緒不過濾、會掃全部租戶**。owner-explicit 的 repository 方法已存在：`AssetSnapshotRepository.findLatestWithStocksByOwnerUserId`、`findDistinctOwnerUserIds`。
- `AssetService.getSnapshotDetail(Long id)` 內部 `findSnapshot(id)` → `toDetailResponse(s)`。
- `SnapshotAggregateCalculator.depositEstimatedInterest`（`amount × rate / 100`，scale 0 HALF_UP；rate null／≤0 或 TRANSIT_* 為 0）是存款利息既有公式。
- 應付在途款（`transit_fund_type.payable=true`）的 amount 已在寫入時轉負；TRANSIT_USD 已用快照匯率換算成台幣。
- `MarketDataService.isTwTradingDayKnown(date)` → `Optional<Boolean>`（空＝未知；週末 false；會經 external-materials 讀權威日曆）。
- 排程慣例：`@Scheduled(cron=…, zone="Asia/Taipei")`；範本 `SnapshotDateRollScheduler`（逐 owner、一 owner 一交易、失敗只 log、`synchronized`）。無 ShedLock；business-services 單一實例。
- `AppUser.isActive()`、`AppUserRepository.findByStatus`。
- 目前 Liquibase 最高版 v1.135.0；`db/schema.sql` 是 schema 唯一標準，須依檔頭指令重產（產生當下表數目前 102）。
- 專案沒有 RFC 8785 JCS 工具；Jackson 預設把 BigDecimal 輸出成 JSON number。

- [ ] 452.3 **`SrppJcs` 與 `SrppDecimal`（`com.steven.assets.srpp`）。**
  - `SrppJcs.canonicalize(JsonNode)`：只接受 object／array／string／boolean／null／絕對值 ≤ 2^53−1 的整數（RFC 8785 以 IEEE-754 double 序列化，超出範圍無法保證一致）；object key 依 `String.compareTo` 排序；字串逸出只處理 `"`、`\`、`\b`、`\f`、`\n`、`\r`、`\t`，其餘 U+0000–U+001F 為 `\u00xx`（小寫 hex），其他字元原樣；無空白。遇浮點、BigDecimal 非整數、絕對值超過 2^53−1 → `IllegalArgumentException`。`sha256Hex(String)` 以 UTF-8 計算小寫 hex。
  - `SrppDecimal.format(BigDecimal)`：`signum()==0` → `"0"`，否則 `stripTrailingZeros().toPlainString()`；`isCanonical(String)` 以 `^-?(0|[1-9][0-9]*)(\.[0-9]*[1-9])?$`、長度 ≤80、不等於 `-0` 判斷。
  - 測試 `SrppJcs` 的單元測試：把 `docs/handoffs/srpp-api-spec-20260923/examples/` 的三份 `summary-*.json` 複製到 `backend/src/test/resources/srpp/`，對每份 `context` 計算 → 必須等於檔內 `contextContentSha256`（三份皆已驗證可達）；七份 `evidence-*.json` 的 `body` 字串 SHA-256 必須等於 `bodySha256`；逸出、排序、非 ASCII、拒絕浮點的單元案例。`SrppDecimal` 的單元測試：`1600000`、`0.05`、`-31004`、`0`（含 `0.00`、`-0.0` 輸入皆輸出 `0`）、`1E+3` 輸入輸出 `1000`；`isCanonical` 反例 `01`、`1.0`、`-0`、`1e3`、`1,000`、`NaN`、空字串。
