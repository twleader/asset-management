## 背景

使用者要求「如果是個股，一定要參考基本面」。t264 已把雷達改為「趨勢品質 × 進場時機」二維決策，但趨勢品質仍 100% 由價格資訊構成。價格已反映的崩壞，基本面往往更早顯示；本任務讓評分能看見公司體質。

## 要做什麼

### 267.1 四個子因子（定義沿用 t224，已審查過）

- [ ] 讀取一律走 `(stock_code, market)` ＋期別排序取最近 N 期。三表**無 `owner_user_id`、不套 `@Filter`**，讀取時不需要也不得加 owner 條件。

  | 子因子 | 定義 | 標準化 | 回 `null` 的條件 |
  |---|---|---|---|
  | EPS 年增率 | 最近四季 `eps` 合計 vs 前四季合計的增率 | `≥+20%` → `+1`、`≤−20%` → `−1`、線性內插 | 不足 8 季；**或前四季合計 `≤ 0`** |
  | ROE | 最近四季 `net_income_parent` 合計 ÷ 最新一期 `equity_parent` | `≥15%` → `+1`、`≤5%` → `−1`、線性內插 | 不足四季；或 `equity_parent ≤ 0` |
  | 月營收 YoY | 最近 3 個月 `revenue_yoy_pct` 的算術平均 | `≥+15%` → `+1`、`≤−15%` → `−1`、線性內插 | 不足 3 個月 |
  | PE 自身歷史分位 | 現行 `pe_ratio` 在該股自身歷史分布中的百分位 | `≤20 百分位` → `+1`、`≥80 百分位` → `−1`、線性內插 | 見 267.2 |

- [ ] **EPS 年增率的負基期**：前四季合計 `≤ 0`（去年虧損）時**必須回 `null`，不得回 `+1`**——由虧轉盈的增率在數學上是正無窮或負值，兩者都會給出錯誤訊號。

### 267.2 PE 子因子的兩種 `null` 語意與優先序（最容易做錯的一項）

- [ ] `stock_valuation_daily` 中有兩種「沒有 PE」，**行為完全相反**：
  - **當日有列但 `pe_ratio IS NULL`** = 公司虧損（無正 EPS 可計算本益比）→ **計為 `−1`**；
  - **當日根本沒有列** = 未抓到 → 回 `null`。
- [ ] **優先序：虧損一律計 `−1`，與歷史樣本量無關**；只有「非虧損但歷史樣本 < 250 交易日」才回 `null`。
  此優先序必須明確實作——**t266 上線首年歷史樣本恆不足**，若無優先序規定則每一家虧損公司的兩個條件同時成立而行為未定義。
- [ ] **PE 低分位的方向性限制**：「PE 處於自身歷史低分位 → `+1`」預設「便宜＝機會」，但長期衰退股的 PE 會持續停在自身歷史低位而**永久**取得正分，恰與本任務要解決的「區分崩壞 vs 錯殺」相衝突。故：**`EPS 年增率 ≤ −20%`（即該子因子為 `−1`）時，PE 分位子因子一律回 `null`**，不得給正分。此交互須有專屬測試。

### 267.3 權重接法（扁平，非 t223 的分組正規化）

- [ ] 四個子因子各自作為獨立因子加入 `Accumulator`，權重合計 `W_FUNDAMENTAL_TOTAL = 0.16`：EPS 年增率 `0.05`、ROE `0.05`、月營收 YoY `0.03`、PE 自身歷史分位 `0.03`。
- [ ] 其餘 14 個因子（t264 落地版）等比例縮減以維持總和 `1.00`，**新權重表須完整列出並以斷言釘住總和**。
- [ ] **ETF 與查無資料者四項全 `null`**，由 `Accumulator` 既有的缺值重分配吸收。**嚴禁以 `0`（＝中性）代替缺值**——否則 ETF 與新掛牌標的會被系統性拉向 50 分。
- [ ] **ETF 判定一律走 Requirement 46 AC（Requirement 46 AC「ETF 判定採資料驅動，跟隨專案既有決策方向」）的三段順序**：(1) `stock.security_type` override（t266 新增該欄）；(2) 資料驅動——該標的在 **ETF 淨值資料**（`etf_nav_history`）中有紀錄即為 ETF；(3) fallback 台股 `00` 開頭。
  **不得以「基本面表整筆不存在」作為 ETF 判準**——該訊號在 t266 已定義為「未抓到」，兩者行為相反（前者預期恆 `null`、後者代表抓取失敗需告警）。用同一個訊號表達兩件事，會讓抓取故障被靜默偽裝成「這是 ETF」。
  **亦不得沿用 `MarketDataService.isEtf()` 或 `MarketDataFetchService.US_ETF_WHITELIST`**——該白名單有兩份複本（backend 與 external 各一），皆把 `AVGO`（Broadcom，個股）誤列為 ETF 且皆漏 `SGOV`；專案既有決策已三度明文記載刻意不複用（`MarketDataFetchService.java:641`、`EtfNavPoller.java:29`、`ExcelExportService.java:795`）。
- [ ] 本任務**不改 t264 的二維動作映射、不改 `buyGate`、不改 `TimingState` 判定**，只改分數。

### 267.4 揭露與版本

- [ ] **`RULE_VERSION` 升版一級**（`V(n)` → `V(n+1)`，**不得寫死字面值**，見檔頭警告），前端兩處 hardcode 同步。新舊版分數不可直接比較（新增四因子並重配權重）。
- [ ] **資料累積時程須於前端揭露**，不得讓使用者誤以為分數已含完整基本面判斷。文案須能表達「本檔目前有幾項基本面子因子生效」，而非籠統宣稱已納入基本面。
- [ ] **跨標的分數可比性的既有界線須一併揭露**：不同標的因缺值而套用不同的實際生效權重（ETF 無基本面、新掛牌無 PE 歷史），分數的組成結構不同，跨標的排序僅供參考。
- [ ] **ROE 的口徑失真須揭露**（Requirement 46 AC「ROE 計算口徑的失真必須揭露」）：本任務以「近四季淨利合計 ÷ 最新一期期末權益」計算（來源未提供平均權益），理由文案**須明確標示為近似值，不得呈現為經審計的正式 ROE**。
- [ ] `reasons`／`risks` 須說明基本面貢獻方向（例：「近四季 EPS 年增 24%，體質正貢獻」「基本面資料累積中，該組權重已重分配」），不得只給總分。
- [ ] **Requirement 44 的通知基準須重建**（沿用 t264 已定義的同一機制：升級後首輪只建基準不寄信）。基本面由「全 `null`」轉為「有值」時分數同樣會跳變，須以相同方式處理。
- [ ] **零 AI API 約束不變**：一律由本地 DB 的結構化數值計算，不得引入 LLM 判讀財報文字、不得於請求鏈觸發外部抓取。

## 驗證
